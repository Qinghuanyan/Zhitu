# TravelHub 界面文案与编码治理说明

更新时间：2026-05-22

## 1. 问题现象

本次排查前，TravelHub 存在两类长期反复出现的问题：

1. **界面英文残留**
   - 首页标题、空状态说明、推荐按钮、地图说明、资料页兜底文案等仍有英文
2. **中文乱码**
   - 同一页面中存在大量类似“鍦”“閳”“娑撴”等 mojibake 文本
   - 文档文件也出现同类问题

## 2. 根因

### 2.1 文案来源分散

TravelHub 的显示文案同时来自三层：

- HTML 静态模板
- HTML runtime 脚本
- Kotlin 原生桥接层生成的状态数据

之前只改了其中一层，另外两层仍保留旧英文或旧乱码，因此问题会反复回灌。

### 2.2 历史 HTML 存在错误编码文本

旧版 HTML 曾被多次复制、备份、脚本替换和再同步。

其中一部分中文文本在某次处理中已经被错误解码，再以 UTF-8 重新保存，最终形成 mojibake。后续如果继续基于这份文件复制，就会把乱码不断扩散。

### 2.3 Windows 文本写入流程不统一

在 Windows 环境下，如果脚本写文件时没有显式指定 UTF-8，或者使用了已经损坏编码的源文本，就很容易把页面和文档再次写坏。

## 3. 本轮治理范围

本轮一次性收口了以下位置：

### 3.1 HTML 静态模板

文件：

- `Zhitu/ai_travel_planner.html`
- `ZhituHtml/ai_travel_planner.html`

处理内容：

- 首页头部文案
- 快捷入口文案
- 输入框占位文案
- 资料页静态模板
- 行程详情 overlay 静态模板
- 偏好设置静态模板
- 住宿详情静态模板

原则：

- 旧 demo 文案不再保留
- 只保留中文空模板或中文占位文案
- 等待原生真实数据注入

### 3.2 HTML runtime 默认文案

文件：

- `Zhitu/.tools/zhitu_runtime.js`

处理内容：

- 空状态
- 推荐卡片按钮
- 详情字段名
- 地图页标题
- 资料页兜底文案
- 行程页兜底文案

原则：

- runtime 中不再保留英文默认 UI 文案
- 所有默认值都必须能直接作为正式中文界面显示

### 3.3 Kotlin 桥接层默认文案

文件：

- `Zhitu/app/src/main/java/me/rerere/rikkahub/ui/pages/travel/TravelHubHtmlPage.kt`

处理内容：

- 推荐分类标题
- 推荐说明
- 推荐空状态
- 排序标签
- 会话标题兜底
- 历史会话 / 当前行程 / 收藏项默认标题
- 导出分享 chooser 文案
- Markdown 导出标题和字段名
- 用户资料默认名称和统计项

原则：

- 原生层写给 HTML 的文本必须默认是中文
- 不允许“HTML 中文 + Kotlin 英文”混用

## 4. 目前已建立的约束

### 4.1 唯一正式 HTML 源

只允许：

`ZhituHtml/ai_travel_planner.html`

作为正式 UI 源。

`Zhitu/ai_travel_planner.html` 只是项目内同步副本。

### 4.2 runtime 独立源

`Zhitu/.tools/zhitu_runtime.js`

作为 runtime 脚本源，修改 runtime 后必须重新同步回 HTML。

### 4.3 旧 demo 不得重新接回主流程

以下内容不得重新成为正式入口：

- `simulateAIResponse`
- `handleSend`
- 旧 mock 卡片渲染函数
- `travel-design/preview/*.html`
- `Zhitu.html`
- `Zhitu2.0.html`

## 5. 后续修改规范

### 5.1 改 UI 文案时必须同时检查三层

任何一次 TravelHub 文案修改，都必须同时检查：

1. HTML 静态模板
2. HTML runtime
3. Kotlin 桥接层默认值

不能只改其中一处。

### 5.2 脚本写文件必须显式 UTF-8

如果用脚本批量写文件，必须显式指定 UTF-8。

推荐方式：

- `apply_patch`
- 或 PowerShell `WriteAllText(..., new UTF8Encoding(false))`

不建议依赖默认编码写入。

### 5.3 优先保留空模板，不保留旧示例中文

对于非正式流程的静态 overlay：

- 可以保留结构
- 但不要再放旧示例目的地、旧示例酒店、旧示例餐厅
- 优先改成“等待原生注入”的中文空模板

### 5.4 修改后必须做两类验证

至少执行：

1. HTML runtime smoke test
2. 编译并在模拟器/真机打开首页截图验证

如果首页仍出现英文或乱码，说明还有未收口的文本来源。

## 6. 推荐维护流程

后续修改 TravelHub 界面时，建议按以下顺序：

1. 改 `Zhitu/.tools/zhitu_runtime.js`
2. 改 `Zhitu/ai_travel_planner.html` 的静态模板
3. 改 `TravelHubHtmlPage.kt` 的默认文案
4. 将 runtime 同步回 `Zhitu/ai_travel_planner.html`
5. 将 `Zhitu/ai_travel_planner.html` 同步到 `ZhituHtml/ai_travel_planner.html`
6. 编译 APK 并截图确认

## 7. 当前结论

这次问题不是“单个字符串没翻译”，而是：

- **文案来源分散**
- **历史乱码模板未清理**
- **编码写入流程不统一**

本轮已经按这三个根因一起收口。后续只要遵守本说明里的维护流程，就不会再反复踩同一类坑。

## 8. 2026-05-22 补充：顶部“开发者模式”乱码根因

### 8.1 现象
- TravelHub 主界面顶部中间会出现一条红色乱码提示。
- 该提示不在 HTML 主内容区内，截图中位于状态栏下方、页面正文上方。

### 8.2 排查结论
- 不是 i_travel_planner.html 正文卡片里的静态文案。
- 不是 Kotlin TopBar / Compose 宿主层文本。
- 不是 document.title、HTML <title> 或页面内普通 DOM 节点直接渲染出的正文。
- 最终验证表明：正式可交付包应优先使用 aseline 变体，而不是默认 debug 变体。

### 8.3 原因说明
- debug 变体在当前设备 / WebView 组合下，会触发一条接近“开发者模式”含义的顶部红色调试提示。
- 即使主页面文案、HTML 编码、runtime 注入全部修正，这条提示仍可能继续出现。
- 该问题属于构建变体 / 调试态表现，不是 TravelHub 业务 HTML 本身继续乱码。

### 8.4 最终处理策略
- 保留新版 HTML 中文化与 runtime 清理逻辑。
- 正式测试 / 交付时，改用：
  - :app:assembleBaseline
  - 输出 APK：pp/build/outputs/apk/baseline/app-universal-baseline.apk
- 该变体已实测：
  - 页面主体中文正常
  - 输入框、快捷入口、主卡片中文正常
  - 顶部红色“开发者模式”乱码不再出现

### 8.5 后续规范
- 需要给用户验收、截图、录屏时，不要直接拿 debug APK 作为最终展示包。
- TravelHub 相关回归默认使用：
  1. 
ode .tools/test_zhitu_runtime.js
  2. gradle :app:assembleBaseline
  3. 安装 pp-universal-baseline.apk
  4. 模拟器/真机截图确认
