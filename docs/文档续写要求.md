# Zhitu 文档续写要求

更新时间：2026-05-22

---

## 1. 目的

本文件用于约束后续任何人更新 `docs/开发文档.md` 时，必须补哪些内容、按什么粒度写、哪些信息不能缺失。

目标：

- 防止文档越写越乱
- 防止只记录“改了什么”但不记录“当前状态是什么”
- 防止功能改了、代码变了、文档没同步
- 防止再次出现乱码、重复章节、状态互相矛盾

---

## 2. 开发文档必须包含的一级章节

每次续写 `开发文档.md`，至少要确保以下一级章节仍然存在且内容同步更新：

1. 项目概述
2. 当前项目定位
3. 当前正式 UI 方案
4. 当前整体架构
5. 当前核心模块
6. 当前 TravelHub 正式交互流程
7. 当前 AI 规划方案
8. 当前 AI Provider / 模型接入状态
9. 当前已完成功能状态
10. 当前已知问题与风险
11. 当前构建与交付状态
12. 当前正式数据与状态模型
13. 当前桥接动作定义
14. 已修复问题记录
15. 后续开发优先级
16. 文件级重点关注清单
17. 文档结论

如果项目结构后续变化，可以增章节，但**不允许把这些核心章节删掉而不迁移内容**。

---

## 3. 每次续写必须同步更新的最小内容

### 3.1 功能改动后必须更新

如果改了功能，必须更新：

- 当前正式流程是什么
- 哪些功能已完成
- 哪些是过渡态
- 哪些旧入口已解绑
- 哪些按钮/动作的语义变了

### 3.2 UI 改动后必须更新

如果改了 UI，必须更新：

- 当前唯一正式 UI 源文件
- 构建后打包路径
- 已废弃的 UI/HTML/原生入口
- 详情页是否还走 HTML
- 交互流是否变化

### 3.3 AI / Provider 改动后必须更新

如果改了模型、Provider、Prompt、多 Agent 流程，必须更新：

- 调用入口
- 当前使用的 prompt 阶段
- fallback 是否启用
- 结构化输出约束是否变化
- 哪些文件是关键点

### 3.4 构建 / APK 改动后必须更新

如果重新打包、改构建、改交付方式，必须更新：

- 当前可交付 APK 路径
- 最近一次验证通过的构建任务
- 使用的 Gradle/构建环境
- 是否已经安装到模拟器/真机验证

### 3.5 Bug 修复后必须更新

每修一个问题，必须追加：

1. 问题表现
2. 根因
3. 修改文件
4. 修复方式
5. 回归结果
6. 防踩坑规则

不允许只写一句“已修复”。

---

## 4. 文档中的状态分类要求

所有功能状态必须明确标成以下三类之一：

### 4.1 已完成且可用

表示：

- 主流程已经接通
- 代码已落地
- 至少做过基础构建验证

### 4.2 已完成但仍需继续回归

表示：

- 代码已经接好
- 但还需要更多真机/模拟器验证
- 或依赖真实数据、真实 provider 场景继续确认

### 4.3 过渡态 / 未完全收口

表示：

- 旧代码仍保留
- 新旧逻辑尚未完全清理
- 还存在潜在误接风险

禁止把所有东西都写成“已完成”，必须如实区分。

---

## 5. 文档必须写清楚的“当前事实”

每次续写，都要优先描述“当前事实”，不要只写历史过程。

必须能让下一个接手的人直接回答下面这些问题：

1. 项目现在的正式 UI 到底是哪份文件？
2. TravelHub 正式主流程现在是什么？
3. 住宿 / 餐饮 / 活动现在点了之后到底会发生什么？
4. 行程规划现在是普通聊天还是内部多 Agent？
5. 当前模型调用入口在哪里？
6. 当前 APK 在哪里？
7. 现在还有哪些旧资源没删？
8. 现在已知还差什么？

如果文档看完后仍回答不了这些问题，说明文档不合格。

---

## 6. 文档写法要求

### 6.1 用“当前状态”写，不要只写“做过什么”

优先写：

- 当前正式入口是……
- 当前主流程是……
- 当前过渡态是……

不要只写：

- 今天改了……
- 本轮尝试了……

### 6.2 写清文件路径

凡是涉及关键改动，尽量写到文件级，例如：

- `app/src/main/java/...`
- `ZhituHtml/ai_travel_planner.html`
- `docs/界面文案与编码治理说明.md`

### 6.3 写清“为什么保留旧东西”

如果某个旧文件没删，必须说明：

- 为什么还保留
- 是否仍参与主流程
- 后续何时可删

### 6.4 写清“验证到什么程度”

每次写构建或功能状态时，必须说明是：

- 仅代码改完
- 已 compile 通过
- 已 assemble 通过
- 已安装到模拟器
- 已做端到端点击验证

---

## 7. 文档严禁遗漏的敏感项处理原则

文档可以写：

- Key/URL 的配置位置
- Provider 路径
- 模型调用链路

文档默认不直接写：

- 明文 API Key

除非明确要求写交接密钥表，否则开发文档正文不承载明文密钥。

---

## 8. 每次续写后的自检清单

更新完 `开发文档.md` 后，必须自检：

- [ ] 更新时间是否已更新
- [ ] 当前正式 UI 源是否写清
- [ ] 当前 TravelHub 主流程是否写清
- [ ] 当前 AI 规划链路是否写清
- [ ] 当前已完成 / 过渡态 / 已知问题是否分开写
- [ ] 当前 APK 路径是否更新
- [ ] 本轮修复是否写了根因和回归结果
- [ ] 是否出现乱码
- [ ] 是否出现重复章节
- [ ] 是否仍能让新人直接理解当前项目状态

---

## 10. 本要求文档的使用规则

以后任何人继续更新：

- `docs/开发文档.md`

前，都应先看：

- `docs/文档续写要求.md`

如果后续项目结构变化较大，也要同步更新本文件，保证“文档怎么写”这件事本身也是可维护的。
