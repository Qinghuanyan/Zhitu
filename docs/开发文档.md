# Zhitu 开发文档

更新时间：2026-05-22

---

## 1. 项目概述

`Zhitu` 是一个以 **Android + Kotlin + Jetpack Compose + WebView/HTML** 为主的 AI 旅行规划应用。

当前项目的核心目标不是做一个通用聊天壳，而是做一个围绕 **TravelHub 旅行规划** 的完整产品闭环：

- 用户输入旅行需求
- AI 解析需求并生成结构化旅行 brief
- 基于目的地、天数、预算、偏好生成行程
- 同步产出住宿 / 餐饮 / 活动推荐
- 在同一套新版 HTML UI 中展示、调整、导出、分享

---

## 2. 当前项目定位

### 2.1 当前主线

当前主线是 **TravelHub 新版 HTML 界面全面替换旧旅行界面，并与原生功能完整对接**。

重点不是“把 HTML 套到旧页面上”，而是：

- 让新版 UI 成为 TravelHub 的唯一正式主界面
- 让 HTML 成为原生旅行能力的展示层
- 让原生 Kotlin 层继续负责真实业务、数据、状态、AI 调度和路由

### 2.2 当前不做的方向

以下内容当前不是主线目标：

- 恢复旧 TravelHub 原生壳作为主入口
- 恢复旧 HTML 设计稿作为正式入口
- 把住宿 / 餐饮 / 活动再次拆回独立原生页

## 4. 当前整体架构

当前 TravelHub 采用“三层结构”：

### 4.1 HTML 展示层

负责：

- TravelHub 主界面视觉
- 对话区、行程区、推荐卡片区、详情展开区的渲染
- 用户点击行为采集
- 通过 bridge 向原生发动作

不负责：

- 真实旅行数据计算
- 行程生成
- 推荐源获取
- 最终状态裁决

### 4.2 Android / Kotlin 原生业务层

负责：

- 会话状态管理
- TravelPlan 生成与持久化
- 旅行目的地上下文
- 推荐数据源合并
- 地图跳转
- 导出 / 分享
- AI Provider 调用
- 失败兜底、回填、排序、清洗

### 4.3 WebView Bridge 桥接层

当前主要通过：

- `WebView`
- `JavascriptInterface`
- `window.__ZHITU_RECEIVE_STATE__(...)`
- HTML 中 `data-zhitu-action`

完成状态注入和动作回传。

## 6. 当前 TravelHub 正式交互流程

### 6.1 启动

当前启动后：

- TravelHub 首页直接加载新版 `ai_travel_planner.html`
- 由原生侧注入完整状态
- HTML 不再自己注入 demo/mock 会话内容

### 6.2 用户输入旅行需求

当前行为：

1. 用户在 HTML 输入框发送消息
2. HTML 派发 `send_message`
3. `TravelHubHtmlPage.kt` 调用 `vm.startTravelPlanning(...)`
4. `ChatVM` 转到 `ChatService.submitTravelPlanningRequest(...)`
5. 不再先走一轮普通聊天回复
6. 直接进入内部旅行规划流水线

### 6.3 生成行程

当前行为：

1. 提取 brief
2. 修正 brief
3. 拉取 planning facts
4. 生成 itinerary payload
5. 审计 payload
6. normalize 强约束
7. enrich 成完整 TravelPlan
8. 注入 HTML 状态

### 6.4 点击住宿 / 餐饮 / 活动

当前正式定义：

- 不跳旧原生页
- 不跳旧 HTML 独立壳页
- 不切回旧 tab 方案

而是：

1. 原生读取当前 `TravelPlan`
2. 取出对应类别推荐
3. 生成 `assistantRecommendation`
4. 在 AI 对话流中直接追加推荐卡片区域

### 6.5 点击推荐卡片

当前正式定义：

- 详情留在 HTML 内部展示
- 不跳旧原生推荐详情页

### 6.6 点击地图

当前行为：

- 通过 `open_map`
- 跳转到原生地图页
- 传递的是高亮 POI 字符串 ID
- 已修复把 POI ID 误当 UUID 解析导致崩溃的问题

### 6.7 导出 / 分享

当前行为：

- 支持导出 Markdown
- 支持分享当前行程

## 7. 当前 AI 规划方案

### 7.1 当前不是“多个可见助手”

当前没有把产品做成多个用户可见 Agent。

当前采用的是：

- **对外：1 个 Travel Planner Assistant**
- **对内：多阶段 Agent 流水线**

### 7.2 当前内部多阶段流程

#### 阶段 1：Brief Extractor

从用户最近旅行需求中提取：

- 目的地
- 天数
- 人数
- 预算
- 风格偏好
- 交通偏好
- 约束条件

#### 阶段 2：Brief Refiner / Constraint Agent

负责：

- 修正提取错误
- 强约束天数
- 清洗 userIntentSummary
- 防止把“3 天”扩成“14 天”

#### 阶段 3：Itinerary Generator

输入：

- brief
- currentPlan
- planning facts
- recent user content

输出：

- `TravelGeneratedPayload`

#### 阶段 4：Itinerary Auditor

负责：

- 审核生成结果
- 强制 `itineraryDays.length == brief.days`
- 强制 `dayIndex` 连续
- 删除 role tag / markdown 脏文本

#### 阶段 5：Deterministic Normalizer

代码层最终兜底：

- 超出天数直接截断
- 不足天数自动补齐
- 对展示文本再次清洗
- 对推荐和 POI 做兜底回填

## 8. 当前 AI Provider / 模型接入状态

### 8.1 当前调用入口

TravelHub 当前仍通过项目现有 Provider 框架调用模型，不是单独写死一个 HTTP 客户端。

关键路径：

- `SettingsStore.getCurrentChatModel()`
- `findProvider(...)`
- `providerManager.getProviderByType(...)`
- `generateText(...)`

### 8.2 当前默认策略

当前 TravelHub 内部使用的是“项目当前聊天模型”作为规划模型来源。

也就是说：

- TravelHub 不是单独维护一套完全独立模型栈
- 而是在现有 Provider/Model 配置体系上执行旅行规划 prompt

### 8.3 当前文档约束

敏感信息（API Key）**不直接写入开发文档正文**。

只记录：

- 配置位置
- 调用路径
- 当前是否启用 fallback
- 需要核对的 Provider 文件

相关位置：

- `Zhitu/ai/src/main/java/me/rerere/ai/provider/ProviderSetting.kt`
- `Zhitu/app/src/main/java/me/rerere/rikkahub/data/datastore/DefaultProviders.kt`

### 8.4 当前需要继续确认的点

虽然 TravelHub 已接入现有 Provider 框架，但仍建议继续核查：

- 当前默认模型是否稳定
- fallback 是否对 TravelHub 规划链路完全生效
- 不同 provider 返回格式差异是否会污染结构化字段
