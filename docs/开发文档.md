# Zhitu 开发文档

更新时间：2026-05-22

---

## 1. 项目概述

`Zhitu` 是一个以 **Android + Kotlin + Jetpack Compose + WebView/HTML** 为主的 AI 旅行规划应用。

当前项目的核心目标不是做一个通用聊天壳，而是做一个围绕 **TravelHub 旅行规划** 的完整产品闭环：

- 用户输入旅行需求
- AI 解析需求并生成结构化旅行 brief
- 基于目的地、天数、预算、偏好生成行程
- 同步产出住宿 / 餐饮 / 活动推荐
- 在同一套新版 HTML UI 中展示、调整、导出、分享

---

## 2. 当前项目定位

### 2.1 当前主线

当前主线是 **TravelHub 新版 HTML 界面全面替换旧旅行界面，并与原生功能完整对接**。

重点不是“把 HTML 套到旧页面上”，而是：

- 让新版 UI 成为 TravelHub 的唯一正式主界面
- 让 HTML 成为原生旅行能力的展示层
- 让原生 Kotlin 层继续负责真实业务、数据、状态、AI 调度和路由

### 2.2 当前不做的方向

以下内容当前不是主线目标：

- 恢复旧 TravelHub 原生壳作为主入口
- 恢复旧 HTML 设计稿作为正式入口
- 把住宿 / 餐饮 / 活动再次拆回独立原生页

## 4. 当前整体架构

当前 TravelHub 采用“三层结构”：

### 4.1 HTML 展示层

负责：

- TravelHub 主界面视觉
- 对话区、行程区、推荐卡片区、详情展开区的渲染
- 用户点击行为采集
- 通过 bridge 向原生发动作

不负责：

- 真实旅行数据计算
- 行程生成
- 推荐源获取
- 最终状态裁决

### 4.2 Android / Kotlin 原生业务层

负责：

- 会话状态管理
- TravelPlan 生成与持久化
- 旅行目的地上下文
- 推荐数据源合并
- 地图跳转
- 导出 / 分享
- AI Provider 调用
- 失败兜底、回填、排序、清洗

### 4.3 WebView Bridge 桥接层

当前主要通过：

- `WebView`
- `JavascriptInterface`
- `window.__ZHITU_RECEIVE_STATE__(...)`
- HTML 中 `data-zhitu-action`

完成状态注入和动作回传。

## 6. 当前 TravelHub 正式交互流程

### 6.1 启动

当前启动后：

- TravelHub 首页直接加载新版 `ai_travel_planner.html`
- 由原生侧注入完整状态
- HTML 不再自己注入 demo/mock 会话内容

### 6.2 用户输入旅行需求

当前行为：

1. 用户在 HTML 输入框发送消息
2. HTML 派发 `send_message`
3. `TravelHubHtmlPage.kt` 调用 `vm.startTravelPlanning(...)`
4. `ChatVM` 转到 `ChatService.submitTravelPlanningRequest(...)`
5. 不再先走一轮普通聊天回复
6. 直接进入内部旅行规划流水线

### 6.3 生成行程

当前行为：

1. 提取 brief
2. 修正 brief
3. 拉取 planning facts
4. 生成 itinerary payload
5. 审计 payload
6. normalize 强约束
7. enrich 成完整 TravelPlan
8. 注入 HTML 状态

### 6.4 点击住宿 / 餐饮 / 活动

当前正式定义：

- 不跳旧原生页
- 不跳旧 HTML 独立壳页
- 不切回旧 tab 方案

而是：

1. 原生读取当前 `TravelPlan`
2. 取出对应类别推荐
3. 生成 `assistantRecommendation`
4. 在 AI 对话流中直接追加推荐卡片区域

### 6.5 点击推荐卡片

当前正式定义：

- 详情留在 HTML 内部展示
- 不跳旧原生推荐详情页

### 6.6 点击地图

当前行为：

- 通过 `open_map`
- 跳转到原生地图页
- 传递的是高亮 POI 字符串 ID
- 已修复把 POI ID 误当 UUID 解析导致崩溃的问题

### 6.7 导出 / 分享

当前行为：

- 支持导出 Markdown
- 支持分享当前行程

## 7. 当前 AI 规划方案

### 7.1 当前不是“多个可见助手”

当前没有把产品做成多个用户可见 Agent。

当前采用的是：

- **对外：1 个 Travel Planner Assistant**
- **对内：多阶段 Agent 流水线**

### 7.2 当前内部多阶段流程

#### 阶段 1：Brief Extractor

从用户最近旅行需求中提取：

- 目的地
- 天数
- 人数
- 预算
- 风格偏好
- 交通偏好
- 约束条件

#### 阶段 2：Brief Refiner / Constraint Agent

负责：

- 修正提取错误
- 强约束天数
- 清洗 userIntentSummary
- 防止把“3 天”扩成“14 天”

#### 阶段 3：Itinerary Generator

输入：

- brief
- currentPlan
- planning facts
- recent user content

输出：

- `TravelGeneratedPayload`

#### 阶段 4：Itinerary Auditor

负责：

- 审核生成结果
- 强制 `itineraryDays.length == brief.days`
- 强制 `dayIndex` 连续
- 删除 role tag / markdown 脏文本

#### 阶段 5：Deterministic Normalizer

代码层最终兜底：

- 超出天数直接截断
- 不足天数自动补齐
- 对展示文本再次清洗
- 对推荐和 POI 做兜底回填

### 8.1 当前调用入口

TravelHub 当前仍通过项目现有 Provider 框架调用模型，不是单独写死一个 HTTP 客户端。

关键路径：

- `SettingsStore.getCurrentChatModel()`

当前 TravelHub 内部使用的是“项目当前聊天模型”作为规划模型来源。

也就是说：

- TravelHub 不是单独维护一套完全独立模型栈
- 而是在现有 Provider/Model 配置体系上执行旅行规划 prompt

- 章节重叠

本次文档已按“当前事实版本”重写。

### 10.2 TravelHub 仍需继续做端到端回归

当前虽然：

- 编译通过
- APK 已产出
- 关键 bug 已修

但仍需继续用模拟器/真机验证：

- 真实发送消息
- 真实生成 3 天行程
- 住宿 / 餐饮 / 活动出卡
- 重规划后同步刷新

### 10.3 旧资源尚未完全清理

当前代码库仍存在：

- 旧 HTML
- 旧原生页
- 过渡文件

风险：

- 后续开发时误接回旧入口
- 文档更新时引用旧路径

### 10.4 生成中会话切换后的恢复不稳定

当前已核对到的事实：

- `ChatService.kt` 在流式生成过程中会持续 `updateConversation()`，但这一步只更新当前 `ConversationSession` 内存态；
- `saveConversation()` 仍主要在生成完成后统一落库；
- `ConversationSession.kt` 会在生成期间保留内存引用，避免 session 立刻释放；
- `Zhitu.html` 里的 `conversation.isGenerating`、`historyConversations`、`profileUiState` 主要依赖宿主实时注入的 `hostState`。

对应风险：

- AI 长时间思考时，用户切去历史页、其他页面或触发页面重建后，再返回原会话，未完成回复不一定能稳定恢复展示；
- 如果生成中途异常结束、WebView 重建或应用被系统回收，中间草稿与界面态可能直接丢失；
- 当前更接近“生成中内存保活”，还不是“生成态可恢复持久化”。

后续建议：

- 对生成中的 assistant 草稿、`isGenerating`、关键界面状态做节流落库；
- 恢复历史会话时优先检查是否存在“未完成生成”并给出恢复/重试提示；
- 明确区分“生成中 / 已中断 / 已完成”三种状态，避免用户误判为无响应。

### 10.5 流式请求缺少 3 分钟超时与自动换模型

当前已核对到的事实：

- `ai/src/main/java/me/rerere/ai/util/SSE.kt` 在建立 `event-stream` 后会主动执行 `call?.timeout()?.cancel()`；
- 同文件 `onRetryChange()` 当前直接忽略，没有自动重试；
- 当前文档只记录了 Provider fallback 仍需继续回归，但还没有落地“单模型最长等待 3 分钟，超时后自动切换候选模型”的正式机制。

对应风险：

- 某个模型响应慢但不报错时，界面可能长时间停留在“思考中”；
- 用户切换页面后更容易误判为生成失败或卡死；
- fallback 能力即使架构上可接，也没有形成稳定的超时切换策略。

后续建议：

- 为单次生成增加明确的 180000ms 级别超时控制；
- 超时后取消当前模型请求，并按预设候选链路自动切换 provider / model；
- 在 UI 上提示“当前模型超时，已切换备用模型”，避免静默失败。

### 10.6 页面返回入口覆盖仍需全量审计

当前状态：

- 主流程页面、历史入口、设置页、地图页等已有可达性验证；
- 但文档中还没有形成“所有页面 / 弹层 / 细节页是否都有明确返回入口”的完整验收清单。

对应风险：

- 某些二级页面或 WebView 细节层可能只能依赖系统返回，缺少界面内明确返回按钮；
- 用户进入深层页面后，回退路径不一致，体验不稳定；
- 后续继续并入新页面时，容易重复出现“能进入、难退出”的问题。

后续建议：

- 按“页面名 / 入口 / 返回按钮 / 返回目标 / 是否支持系统返回”建立全量 QA 清单；
- 优先检查历史页、收藏页、推荐详情、地图全屏、设置二级页、弹层式详情页；
- 把缺失返回入口的问题统一收敛到一轮导航回归里处理。

### 10.7 定位文案与真实位置名称不一致

当前已核对到的事实：

- `ChatMapDrawer.kt` 里存在固定文案常量 `DEVICE_LOCATION_LABEL = "设备定位"`；
- `buildLocationPoint()` 生成定位摘要时也直接 `append("设备定位")`；
- 但同一段逻辑已经能拿到真实的 `poiName` 与 `address`。

对应风险：

- 地图点位本身可能已经显示真实位置，但旁边说明文案仍是泛化的“设备定位”，与用户理解不一致；
- 当真实 POI 名称已经可得时，继续显示“设备定位”会让用户误以为定位还没完成或结果不准确。

后续建议：

- 有 `poiName` / `address` 时优先展示“当前位置”或直接展示真实地点名；
- 仅在拿不到任何地点语义信息时，才回退为“设备定位”这类泛化描述。
